════════════════════════════════════════════════════════════════════════════════
  PART 1 — WHAT IS THE TENANT SYSTEM?
════════════════════════════════════════════════════════════════════════════════

The Prompt Library is a MULTI-TENANT SaaS platform. Every piece of data — users,
prompts, teams, roles, requests, audit logs, API keys — belongs to exactly one
TENANT. Tenants are completely isolated from each other. A user in tenant "acme"
can never see, touch, or even know about data in tenant "academian".

A TENANT is an organization. They log in with an "org code" (the slug), like:
  - "academian"
  - "acme-corp"
  - "my-school"

There is one special reserved level above all tenants: the PLATFORM ADMIN.
The platform admin uses the reserved org code "platform" to log in, and can
manage all tenants, create new ones, and view everything across the system.

IMPORTANT: The string "platform" is hard-blocked as a tenant slug. No tenant
can be created with slug "platform". It is reserved exclusively for platform
administrator access.


════════════════════════════════════════════════════════════════════════════════
  PART 2 — THE TWO-TIER IDENTITY MODEL
════════════════════════════════════════════════════════════════════════════════

TIER 1: PLATFORM ADMIN
  - User row: is_platform_admin = TRUE, tenant_id = NULL
  - Role: "admin" with ALL 19 permission codes (including tenants.read, tenants.manage)
  - Logs in with org code "platform" (or ticks "Platform administrator" checkbox)
  - Can list/create/update/suspend any tenant
  - Can create/edit/delete users in any tenant
  - When calling tenant-scoped GET endpoints: sees ALL rows unless ?tenant_id= is passed
  - When calling write endpoints: must provide tenant_id in request body

TIER 2: TENANT USER
  - User row: is_platform_admin = FALSE, tenant_id = <uuid>
  - Permanently bound to exactly one tenant — can never cross into another
  - Gets one of: tenant_admin, prompt_manager, or user role
  - Sees only data belonging to their own tenant — enforced at ORM query level

There is NO third level. An API key is always tenant-scoped (never platform-scoped).
Microsoft OAuth users always land in a specific tenant — never at platform level.


════════════════════════════════════════════════════════════════════════════════
  PART 3 — THE TENANT DATABASE MODEL
════════════════════════════════════════════════════════════════════════════════

TABLE: tenants
  id                    VARCHAR(36)   UUID primary key
  slug                  VARCHAR(64)   UNIQUE — the org code users type to log in
                                      Rules: lowercase, alphanumeric + hyphens,
                                      must start/end with letter or number,
                                      max 64 chars, cannot be "platform"
  name                  VARCHAR(200)  Display name ("Academian", "Acme Corp")
  max_users             INTEGER       License cap — max number of active users
  status                VARCHAR(20)   "active" | "suspended"
                                      Suspended = nobody from this tenant can log in
  microsoft_auth_enabled BOOLEAN      Whether MS sign-in is allowed for this tenant
  azure_tenant_id       VARCHAR(64)   Tenant's own Azure AD tenant (overrides platform)
  azure_client_id       VARCHAR(64)   Tenant's own Azure app client ID
  azure_client_secret   VARCHAR(512)  Tenant's own Azure app secret (stored in plain)
  azure_new_user_role   VARCHAR(32)   Role given to auto-provisioned MS users
                                      ("user" | "prompt_manager" | "tenant_admin")
  allowed_email_domains VARCHAR(500)  Comma-separated, e.g. "academian.com,academian.edu"
                                      If set, only these MS email domains can enter
  created_at            TIMESTAMP
  created_by            VARCHAR(100)  Username of platform admin who created it

TABLE: users
  id                    VARCHAR(36)   UUID primary key
  tenant_id             VARCHAR(36)   FK → tenants.id (NULL for platform admins)
  is_platform_admin     BOOLEAN       TRUE only for platform-level admin accounts
  username              VARCHAR(100)  UNIQUE per tenant (same username can exist in two tenants)
  email                 VARCHAR(255)  UNIQUE per tenant
  microsoft_oid         VARCHAR(64)   UNIQUE per tenant (Azure object ID)
  password_hash         VARCHAR(255)  bcrypt hash (NULL for pure Microsoft users)
  display_name          VARCHAR(200)
  role                  VARCHAR(20)   Legacy string: "admin"|"tenant_admin"|"prompt_manager"|"user"
  role_id               VARCHAR(36)   FK → roles.id (new RBAC — overrides string role)
  team_id               VARCHAR(20)   FK → teams.id (primary team assignment)
  active                BOOLEAN       Inactive users cannot log in; don't count against license
  created_at, created_by, last_login_at

UNIQUE CONSTRAINTS ON USERS:
  (tenant_id, username)       — same username allowed in different tenants
  (tenant_id, email)
  (tenant_id, microsoft_oid)

TABLE: roles
  id           VARCHAR(36)   UUID PK
  tenant_id    VARCHAR(36)   FK → tenants.id  (NULL for the global platform "admin" role)
  name         VARCHAR(64)   UNIQUE per tenant
  description  VARCHAR(255)
  is_system    BOOLEAN       TRUE = cannot be deleted (seeded system roles)

  System roles seeded per tenant: tenant_admin, prompt_manager, user
  Platform role (tenant_id=NULL): admin

TABLE: tenant_api_keys
  id           VARCHAR(36)   UUID PK
  tenant_id    VARCHAR(36)   FK → tenants.id (CASCADE delete)
  name         VARCHAR(100)
  key_prefix   VARCHAR(24)   First 16 chars of the key (used for DB lookup)
  key_hash     VARCHAR(255)  bcrypt hash of the full key
  scopes       JSON          List of permission codes the key grants
  active       BOOLEAN
  created_at, created_by
  last_used_at               Updated on every successful validation
  expires_at                 Optional — NULL means never expires


════════════════════════════════════════════════════════════════════════════════
  PART 4 — REQUEST AUTH FLOW (happens on EVERY request)
════════════════════════════════════════════════════════════════════════════════

Flask runs init_request_auth() as a before_request hook for every call.

Step 1: Look for Authorization: Bearer <token> or X-API-Key: <token> header.

Step 2a: If token present AND starts with "pl_live_":
  - Look up key by prefix in tenant_api_keys where active=TRUE
  - bcrypt-compare full token against key_hash
  - Check expires_at if set
  - Check tenant.status == "active"
  - Build AuthContext(auth_type="api_key", tenant_id=key.tenant_id,
                      permissions=frozenset(key.scopes), is_platform_admin=False)
  - Store in Flask g.auth_context

Step 2b: If token present but DOES NOT start with "pl_live_":
  - Set g.invalid_bearer = True
  - Any route with @api_login_required or @require_permission returns 401
    {"error": "Invalid API key"}

Step 3: If no token:
  - Build session auth context from Flask session cookie
  - AuthContext(auth_type="session", tenant_id=session["tenant_id"],
                permissions=frozenset(session["permissions"]),
                is_platform_admin=session["is_platform_admin"])
  - Store in Flask g.auth_context

Step 4: If no session either:
  - g.auth_context = None
  - Any protected route returns 401 {"error": "Login required"}

The AuthContext is the single source of truth for the entire request. All
permission checks, tenant scoping, and identity lookups read from it.

════════════════════════════════════════════════════════════════════════════════
  PART 6 — TENANT SCOPING IN CODE
════════════════════════════════════════════════════════════════════════════════

Every database query that touches tenant-owned data is scoped by:

  apply_tenant_filter(query, Model)
    - API key: always filters by key.tenant_id
    - Platform admin: filters by ?tenant_id= if provided; shows ALL if not
    - Regular user: always filters by session.tenant_id

  get_scoped(Model, pk)
    - Wraps apply_tenant_filter + .first()
    - Used for single-row lookups to prevent cross-tenant ID guessing

  require_tenant_id_for_write()
    - API key: returns key.tenant_id (aborts 403 if somehow missing)
    - Platform admin: reads tenant_id from request body or query string (aborts 400 if missing)
    - Regular user: returns session.tenant_id (aborts 403 if missing)

FILE STORAGE:
  Attachments are stored at: ATTACHMENTS_DIR/<tenant_id>/<filename>
  So even the filesystem is isolated by tenant.

AUDIT EVENTS:
  audit_events.tenant_id is set to the current session's tenant_id.
  Platform admin events have tenant_id = NULL.


════════════════════════════════════════════════════════════════════════════════
  PART 7 — LOGIN FLOWS
════════════════════════════════════════════════════════════════════════════════

────────────────────────────────────────────────
  7A. LOCAL LOGIN
────────────────────────────────────────────────

POST /api/auth/login
Body: { "tenant_slug": "<slug>", "username": "<user>", "password": "<pass>" }

For platform admin:
  Body: { "tenant_slug": "platform", "username": "<user>", "password": "<pass>" }
  OR:   { "platform_admin": true, "username": "<user>", "password": "<pass>" }

What happens server-side:
  1. Normalize slug to lowercase
  2. If slug != "platform": look up Tenant by slug, check status == "active"
  3. Look up User by (slug→tenant_id, username)
  4. bcrypt-verify password
  5. Check user.active == True (403 if deactivated)
  6. Update user.last_login_at
  7. Call establish_session(user) → writes to Flask session cookie
  8. Log audit event auth.login

Edge case: a platform admin can log in using any tenant's slug (or "platform").
If credentials match a platform admin account, they get platform admin context
regardless of which slug they typed.

────────────────────────────────────────────────
  7B. MICROSOFT OAUTH LOGIN
────────────────────────────────────────────────

Step 1: Browser navigates to:
  GET /login/microsoft?tenant_slug=<slug>

  Server:
  - Looks up tenant by slug, checks status == "active"
  - Checks microsoft_auth_enabled on tenant
  - Resolves Azure credentials (tenant's own or platform-wide)
  - Generates CSRF state token, stores in session
  - Stores tenant_slug in session as "oauth_tenant_slug"
  - Redirects to Microsoft authorize URL

Step 2: Microsoft redirects back to:
  GET /auth/microsoft/callback?code=<code>&state=<state>

  Server:
  - Validates state matches session (CSRF protection)
  - Calls msal to exchange code for claims (oid, email, name)
  - Calls find_or_create_user(claims, tenant_slug):
      a. Tries to find existing user by microsoft_oid
      b. Falls back to find by email
      c. Falls back to find by username_base(email)
      d. If found: links OID/email if not already linked, checks active
      e. If not found: checks license cap, checks allowed_email_domains,
         creates new User with role from tenant.azure_new_user_role
  - establish_session(user)
  - Redirects to frontend (SPA)

DOMAIN ALLOWLIST:
  If tenant.allowed_email_domains is set (e.g. "academian.com,academian.edu"),
  then any Microsoft account whose email is NOT in that domain list is rejected
  with: "This Microsoft account is not authorized for organization '<slug>'."

MICROSOFT CREDENTIALS RESOLUTION ORDER (per-tenant first, then platform):
  azure_tenant_id:    tenant.azure_tenant_id  || Config.AZURE_TENANT_ID  || "common"
  azure_client_id:    tenant.azure_client_id  || Config.AZURE_CLIENT_ID
  azure_client_secret: tenant.azure_client_secret || Config.AZURE_CLIENT_SECRET


════════════════════════════════════════════════════════════════════════════════
  PART 8 — API KEY AUTH (MACHINE-TO-MACHINE)
════════════════════════════════════════════════════════════════════════════════

API keys are always tenant-scoped. A key can NEVER be a platform admin key.

KEY FORMAT: pl_live_<24 random URL-safe bytes>
            First 16 characters ("pl_live_xxxxxxxx") are stored as key_prefix for lookup.
            Full key is bcrypt-hashed and stored as key_hash.

SCOPE PRESETS:
  read_only:
    prompts.read, teams.read

  prompt_manager:
    prompts.read, prompts.write, prompts.delete,
    teams.read, reviews.read_all,
    requests.read_all, requests.manage

  full_integration:
    All tenant codes EXCEPT integration.manage
    (keys cannot create more keys — prevents privilege escalation)

HOW VALIDATION WORKS:
  1. Extract prefix (first 16 chars) from the incoming token
  2. SELECT FROM tenant_api_keys WHERE key_prefix = <prefix> AND active = TRUE
  3. bcrypt-compare full token against each candidate's key_hash
  4. If match: check expires_at, check tenant.status == "active"
  5. Update last_used_at
  6. Build AuthContext with tenant_id, permissions=frozenset(key.scopes),
     is_platform_admin=False

RESTRICTIONS FOR API KEY CALLERS:
  - Cannot access: /api/platform/tenants/* (blocked by before_request guard)
  - Cannot access: /api/integration/keys (integration management is session-only)
  - Cannot access: /api/auth/* (login/logout/me — session-only)
  - is_platform_admin is always False regardless of scopes


════════════════════════════════════════════════════════════════════════════════
  PART 9 — TENANT LIFECYCLE (LICENSE + SUSPENSION)
════════════════════════════════════════════════════════════════════════════════

LICENSE ENFORCEMENT:
  tenant.max_users is the cap on ACTIVE users.
  assert_can_add_user() is called before:
    - Creating a user (both by tenant admin and platform admin)
    - Reactivating a deactivated user
    - Microsoft auto-provisioning a new user

  If count(active users) >= max_users:
    Returns 403: "User license limit reached (N/M). Contact your platform administrator."

  Deactivated users (active=FALSE) do NOT count toward the cap.
  Deleting a user frees up a seat immediately.

SUSPENSION:
  Set tenant.status = "suspended" via PUT /api/platform/tenants/<id>
  Effect:
    - Any login attempt (local or Microsoft) gets 403 "This organization has been suspended."
    - Any API key belonging to this tenant stops working (validate_api_key checks status)
    - Existing sessions remain valid until cookie expires or browser closes
      (no immediate session invalidation — consider that a known gap)

  PART 12 — COMMON ERROR RESPONSES
════════════════════════════════════════════════════════════════════════════════

401 {"error": "Login required"}
  — No session cookie and no API key header.

401 {"error": "Invalid API key"}
  — Bearer token present but does not match any active key, or is expired.

403 {"error": "Insufficient permissions"}
  — Authenticated but missing required permission code.

403 {"error": "Tenant context required"}
  — Platform admin called a tenant-scoped endpoint without providing tenant_id.

403 {"error": "This endpoint requires a browser session login"}
  — API key tried to call a session-only endpoint (platform_tenants, integration).

403 {"error": "User license limit reached (N/M). Contact your platform administrator."}
  — Tried to create or reactivate a user at max capacity.

403 {"error": "Your account has been deactivated. Contact an admin."}
  — Login attempt with active=FALSE user.

403 {"error": "This organization has been suspended."}
  — Login attempt against a tenant with status="suspended".

404 {"error": "Unknown organization code"}
  — tenant_slug not found in tenants table during login or tenant-login lookup.

409 {"error": "Username already exists"}
  — Create user with duplicate (tenant_id, username).

409 {"error": "Organization code already exists"}
  — Create tenant with duplicate slug.

400 {"error": "tenant_id required for platform admin"}
  — Platform admin POST/PUT without providing tenant_id in body.

400 {"error": "Organization code must be lowercase letters, numbers, and hyphens"}
  — Slug validation failed.

400 {"error": "Reserved organization code"}
  — Tried to create a tenant with slug="platform".


════════════════════════════════════════════════════════════════════════════════
  PART 13 — KEY DESIGN DECISIONS / GOTCHAS
════════════════════════════════════════════════════════════════════════════════

1. USERNAMES ARE UNIQUE PER TENANT, NOT GLOBALLY.
   "alice" in tenant "acme" and "alice" in tenant "academian" are two completely
   different users. The DB constraint is (tenant_id, username) — not just username.

2. PLATFORM ADMIN HAS NO TENANT_ID.
   session["tenant_id"] is NULL for platform admins. This is by design.
   apply_tenant_filter() detects this and returns all rows (or filters by
   ?tenant_id= if provided).

3. SESSION PERMISSIONS ARE CACHED AT LOGIN TIME.
   session["permissions"] is written when establish_session() is called.
   If you change a user's role, their existing session still has the OLD permissions
   until they log out and log back in. The /api/auth/me endpoint re-fetches and
   refreshes the session, so the frontend can call /me to get fresh permissions.

4. API KEYS HAVE HARD RESTRICTIONS:
   - Cannot be platform admin (is_platform_admin always False)
   - Cannot manage integration (integration.manage excluded from full_integration)
   - Cannot access platform_tenants endpoints
   - Cannot access auth endpoints (login/logout/me)

5. SUSPENDED TENANTS:
   - All new logins are blocked
   - All API keys are invalidated immediately
   - But existing sessions remain valid until they expire
   - There is no active session kill mechanism currently

6. SOFT DELETES ON PROMPTS.
   DELETE sets deleted_at = now(). The prompt is not physically removed.
   base_prompt_query() always filters WHERE deleted_at IS NULL.
   Attachments, versions, reviews, etc. remain linked but are unreachable.

7. ATTACHMENT FILE STORAGE IS TENANT-ISOLATED.
   ATTACHMENTS_DIR/<tenant_id>/<filename>
   Even if someone guesses a stored_name, they cannot download it via the API
   because get_scoped() checks tenant ownership before serving the file.

8. ROLE SEEDING IS PER-TENANT.
   When a tenant is created, 3 system roles (tenant_admin, prompt_manager, user)
   are created with tenant_id = the new tenant's id. These are copies — not shared.
   The global platform "admin" role has tenant_id = NULL and is created once at
   startup by ensure_rbac_seeded().

9. MICROSOFT AUTH CAN USE PER-TENANT AZURE APP REGISTRATIONS.
   A large enterprise tenant might want their own Azure app. Platform provides
   fallback credentials for smaller tenants. Resolution order:
     tenant.azure_* fields → Config.AZURE_* env vars → "common" authority

10. LICENSE IS COUNTED ON ACTIVE USERS ONLY.
    Deactivating a user immediately frees a seat. This is how you "scale down"
    without deleting data — deactivate instead of delete.
