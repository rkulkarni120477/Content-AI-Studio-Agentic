TICKET: "Reviewer dropdown displays users from other tenants while
         submitting content for review" (Editor -> Submit for Review)
================================================================================

--------------------------------------------------------------------------------
0. ASSESSMENT (read this first)
--------------------------------------------------------------------------------
This is almost certainly NOT a new bug. It is the same root cause as three
earlier tickets this week, already fixed and merged to `develop` (PR #110,
commits 5acd7c4 / 9b0f9b8 / 9de9b20 / 405bd88, merged 2026-08-26T13:05:55Z).
The ticket is most likely describing behavior from BEFORE that fix reached
whichever environment was tested.

Evidence:
  - The Editor's "Submit for Review" dropdown (EditorPage.jsx -> EditorBlockCard.jsx)
    and the Workflow page's reviewer dropdown are TWO UIs sharing ONE backend
    endpoint (GET /api/v1/users/reviewers) and ONE repository function
    (user_repository.list_reviewers_and_admins). Both were already fixed
    server-side. There is no second/independent code path for the Editor.
  - Confirmed via full-repo search: no other router or repository function
    assembles a reviewer list; EditorBlockCard.jsx has no fetch of its own,
    it only renders the `reviewers` prop EditorPage.jsx passes down.
  - The usernames in the screenshot (AIM, AIM1, AIM2, AIMadmin, platformadmin,
    platformadmin1, cenuser, ...) match, almost verbatim, the pre-fix symptom
    described in commit 9b0f9b8's own message.
  - `prod` and `develop` diverged well before any of this week's
    reviewer-scoping fixes (29 commits separate them as of this writing,
    verified via a fresh `git fetch` + `git merge-base --is-ancestor`).
    `prod` has NEVER had this fix.
    If the ticket was tested against cas.academian.com (prod), this alone
    fully explains it — no code change needed, only a promotion.
  - If it was tested against cas-dev.academian.com (dev), the fix reached
    `develop` at 13:05 on 2026-08-26 and backend-dev-deploy.yml deploys
    automatically on push to `develop`. A test run before that time, or a
    deploy that silently failed, would show the same symptom.

CONCLUSION: the fix likely already exists; what's missing is confirming WHICH
build was tested and, if it's prod, promoting the fix there. Phase 1 exists
to settle that before touching anything else.
