0. READ THIS FIRST — TWO FINDINGS THAT CHANGE THE ORIGINAL PLAN
--------------------------------------------------------------------------------

FINDING A — DIS S3 keys ALREADY partition by environment.
  Every DIS upload key is built as:
      raw/<namespace>/<ENVIRONMENT>/<job_id>/<relative_path>
  See dis_backend/api/routers/ingestion.py:544-550
      env_name = get_settings().environment or "development"
      s3_key   = f"raw/{namespace}/{env_name}/{job_id}/{safe_rel_path}"
  Same pattern for batch (ingestion.py:636) and folder-scan (ingestion.py:930),
  and for processed/ and generated/ prefixes via
  dis_backend/services/source_library.py:63-77 and
  dis_backend/services/artifacts.py:79-81.

  CONSEQUENCE — AND THIS IS THE DATA-LOSS TRAP:
  If you change ENVIRONMENT on the existing (soon-to-be-prod) server, every
  existing object stops being found, because the code will look under a NEW
  path. In particular the Source Library index lives at
      processed/<namespace>/<ENVIRONMENT>/source_index/source_list.json
  (source_library.py:68-69). Change ENVIRONMENT and DIS reads a different,
  non-existent key, creates a fresh empty one, and the Source Library UI goes
  blank. The files are still in S3 but nothing references them.
  => Phase 1 exists specifically to prevent this. Do not skip it.

FINDING B — The Source Library list is NOT in Postgres.
  The original premise was "files get stored in postgres". Partly true:
    - The Source Library listing users actually see is a single JSON blob in
      S3 (source_list.json above), read/written by
      dis_backend/services/source_library.py:307 / :326 / :366.
    - Job state is in memory or Redis, not Postgres
      (dis_backend/services/job_store.py:142-148).
    - Postgres (dis.dis_documents / dis.dis_jobs) holds the *structured*
      record of each ingested document.
  So bifurcating Postgres alone would NOT separate the Source Library. S3 and
  OpenSearch must be handled too. All three are covered below.

  * Prod KEEPS PROD_CURRENT_ENV unchanged. Do not "tidy" it to "production"

    - Otherwise set dev to "development".
  * Because dev also gets its own bucket AND its own database, a value collision
    would not actually mix data — but keep them distinct anyway so logs, keys and
    the new environment column stay readable.

3. PHASE 2 — FIX THE DEV FRONTEND DEPLOY  [BLOCKER, DATA LOSS]
--------------------------------------------------------------------------------
THE PROBLEM
  .github/workflows/frontend-dev-deploy.yml:55-59 runs:
      aws s3 sync dist/ s3://content-ai-studio-dev/ --delete --exclude "index.html"
  That targets the BUCKET ROOT with --delete. --delete removes every object in
  the destination that is not in the source. The moment DIS starts writing
  DIS/... into content-ai-studio-dev, the next push to `develop` deletes all of
  it. Silently. There is no S3 versioning assumption to fall back on unless it
  is enabled on that bucket.

  Prod does NOT have this problem: frontend-deploy.yml:56-60 syncs to
      s3://content-ai-studio/CAS/
  a sub-prefix, so --delete is scoped to CAS/ and cannot touch DIS/.

THE FIX (mirror prod)
  a) Edit .github/workflows/frontend-dev-deploy.yml:
       - add to the env: block (around line 16-18):
             S3_PREFIX: CAS
       - change the sync and cp steps to include the prefix, exactly as
         frontend-deploy.yml:56-64 does:
             aws s3 sync dist/ s3://${{ env.S3_BUCKET }}/${{ env.S3_PREFIX }}/ \
               --delete --cache-control "..." --exclude "index.html"
             aws s3 cp dist/index.html \
               s3://${{ env.S3_BUCKET }}/${{ env.S3_PREFIX }}/index.html \
               --cache-control "no-cache,no-store,must-revalidate"

  b) CloudFront must follow, or cas-dev.academian.com 404s.
     Distribution E142R1AI8LOAMH (named at frontend-dev-deploy.yml:18):
       - set the S3 origin's Origin Path to  /CAS
       - keep Default Root Object as index.html
       - if a CloudFront Function / Lambda@Edge rewrites SPA routes, confirm it
         still resolves with the origin path applied
       - invalidate /* after the change

  c) ORDER MATTERS. Do (a) + (b) and confirm the dev site loads BEFORE pointing
     DIS at content-ai-studio-dev in Phase 3. If DIS writes first, one deploy
     wipes it.

  d) Belt and braces (recommended regardless):
       - enable S3 Versioning on content-ai-studio-dev
       - optionally add a bucket lifecycle rule to expire noncurrent versions
         after ~30 days so versioning does not grow unbounded

VERIFY
  - Push a trivial frontend change to `develop`.
  - Confirm objects land under s3://content-ai-studio-dev/CAS/
  - Confirm https://cas-dev.academian.com/ still loads and hard-refreshes clean.
  - Put a throwaway object at s3://content-ai-studio-dev/DIS/canary.txt, deploy

5. PHASE 4 — POSTGRES BIFURCATION (SEPARATE DATABASES)  [decision D2]
--------------------------------------------------------------------------------
Principle: the EXISTING dis_db becomes PROD. Nothing moves. Dev gets a new,
empty database. This is the zero-data-movement path and directly satisfies
"we won't miss or lose those files".

Note the existing host is literally named dis-dev-postgres. That name is now
misleading, but renaming an RDS instance is disruptive and is NOT part of this
work. Treat the name as cosmetic debt; record it in Appendix B.

5.1 Provision the dev database
    AUTOMATED — you do not need to run CREATE DATABASE by hand. indexing.py's
    rds_upsert() now calls _ensure_database_exists() first, which creates the
    target database if it's missing (requires dis_user to have CREATEDB —
    it's the owner of the existing dis_db, so it very likely already does).
    Just set the DSN below with a database name that doesn't exist yet, and
    the first upload after this code is deployed creates it. If you'd rather
    provision it explicitly ahead of time (e.g. to run the backfill in 7.3
    before any dev traffic exists), Option 1 below still works exactly as
    written — the auto-create is idempotent either way.

    Option 1 (manual, still supported): a new DATABASE on the same RDS instance.
        CREATE DATABASE dis_db_dev OWNER dis_user;
      Dev DSN: postgresql://dis_user:<pw>@dis-dev-postgres...:5432/dis_db_dev
    Option 2 (strongest isolation): a separate RDS instance for dev.
      Better blast-radius separation; more cost and another security group to
      manage. Choose this if dev traffic could realistically affect prod load.

    Either way DIS self-creates its schema and tables on first write —
    ensure_schema() at indexing.py:54-99 runs CREATE SCHEMA IF NOT EXISTS +
    CREATE TABLE IF NOT EXISTS on every upsert. No manual DDL, no Alembic.
    Confirm structure_store.auto_create_schema is true (it is, in all client
    YAMLs) and that dis_user can CREATE SCHEMA in the new database.

5.2 Point each environment at its own DSN — dis_backend/.env
    PROD:
      DIS_STRUCTURE_STORE_URL=postgresql://dis_user:<pw>@dis-dev-postgres.co7gbazco3kw.us-east-1.rds.amazonaws.com:5432/dis_db
    DEV:
      DIS_STRUCTURE_STORE_URL=postgresql://dis_user:<pw>@dis-dev-postgres.co7gbazco3kw.us-east-1.rds.amazonaws.com:5432/dis_db_dev

    Setting the env var means the YAML literal is ignored entirely, on both
    boxes independently (settings.py:361-370 applies the override
    unconditionally, per environment, before anything reads the config) —
    REVISED from the original draft of this plan: the client YAMLs are
    deliberately left untouched, not edited later either. Confirmed by
    reading _apply_store_env_overrides directly: it does not require the
    YAML to use a ${VAR} placeholder, it overwrites converted["structure_
    store"]["url"] outright whenever the env var is set. Leaving the
    committed literal in place costs nothing once the env var is set (dead
    value, never read), and means a box that hasn't had the env var set yet
    still runs exactly as it does today instead of failing to connect.

    Per-client override exists if a client ever needs its own DB:
      DIS_STRUCTURE_STORE_URL_AIM, DIS_STRUCTURE_STORE_URL_CENGAGE

    URL-ENCODING WARNING: the committed password contains '#'
    (Academian%23123 in aim.yaml:519 — already percent-encoded). Keep it encoded
    in the DSN; a raw '#' truncates the connection string at the fragment.

5.3 Security group
    Ensure the DEV EC2 box's IP/SG is allowed to reach the RDS instance.
    settings.py:274-297 records that this SG currently admits a single
    hardcoded /32 — expect to add one. Do NOT widen it to 0.0.0.0/0.

VERIFY

needed. The backfill UPDATE in 7.3 below is still a manual, one-time step —
run it once you've confirmed which rows in the real database are prod's.

With D2 (separate databases) the column is NOT required for isolation — the
databases cannot see each other. It is still worth adding, cheaply, because:
  * it makes a misconfiguration visible instead of silent. If someone copies the
    prod DSN into the dev .env, rows land in prod tagged "dev" and a one-line
    query finds them.
  * it survives a future decision to merge the databases back.
  * it makes the S3 URLs in each row self-describing during support work.

7.1 Value source  [decision D3]
    Stamp it server-side from get_settings().environment — the SAME value that
    already goes into the S3 key at ingestion.py:545. Do NOT derive it from the
    request Host/Origin: the pipeline runs in a background task
    (ingestion.py:595-600) with no request context, and a client-supplied header
    must never decide which environment a row belongs to.

    `state` already carries everything needed; env is one call away.

7.2 Where it was added  [DONE — this is now "as-built", not a to-do]
    dis_backend/services/indexing.py
      a) rds_upsert() computes `environment = get_settings().environment or
         "development"` once per call and threads it through every upsert_*.
      b) ensure_schema() — CREATE TABLE IF NOT EXISTS is a no-op on a table
         that already exists, so a loop of idempotent ALTERs follows the six
         CREATEs:
             ALTER TABLE {schema}.{table} ADD COLUMN IF NOT EXISTS environment text
         for dis_jobs, dis_documents, dis_content_units, dis_course_calendars,
         dis_calendar_days, dis_syllabus. Denormalised to every child table,
         matching how tenant_id/client_id are already handled.
      c) Two new indexes: idx_dis_documents_environment,
         idx_dis_units_environment.
      d) `environment` added as a column on all six INSERTs (upsert_job,
         upsert_document, upsert_content_units, upsert_calendar +

    NOTE: there is no Alembic for the dis schema. This was NOT added as a
    migration in migrations/versions/ — that chain (head 000100000025)
    belongs to the CAS promptops_db, a different database entirely. The
    ALTERs in ensure_schema() are the correct mechanism here and run
    automatically the next time either environment ingests a file after this
    code is deployed — no manual DDL required to GET the column. Manually
    running the ALTERs first (see 7.3) is only useful if you want the column
    to exist before deploying, e.g. to run the backfill ahead of time.

7.3 Backfill existing rows as prod
    Run ONCE, against the PROD database only:
        UPDATE dis.dis_jobs           SET environment = 'prod' WHERE environment IS NULL;
        UPDATE dis.dis_documents      SET environment = 'prod' WHERE environment IS NULL;

        UPDATE dis.dis_syllabus       SET environment = 'prod' WHERE environment IS NULL;
    Take an RDS snapshot first. Run the ALTERs (via one upload, or manually)
    BEFORE the UPDATEs.

    Decide and write down the vocabulary now, because it must match what the

12. ROLLBACK
--------------------------------------------------------------------------------
Every change in Phases 3-5 is an environment variable. Rollback is: remove the
var, restart the container, and the YAML literal takes over again — which is the
current behaviour. Specifically:

  * Unset DIS_S3_BUCKET          -> back to YAML (content-ai-studio)
  * Unset DIS_STRUCTURE_STORE_URL-> back to YAML (dis_db)
  * Unset DIS_VECTOR_STORE_INDEX_*-> back to YAML (dis-content-dev-*)
  * Do NOT roll back Phase 2 (the frontend prefix). It is strictly safer than
    the current state, and rolling it back re-arms the --delete blast radius.
  * The Phase 6 column is additive and nullable; leaving it in place is harmless
    even if everything else is reverted.

Nothing in this plan deletes or moves an existing object or row. The only
destructive operations are the ones Phase 2 exists to prevent.

APPENDIX A — OPTIONAL LATER: RENAME PROD'S ENVIRONMENT VALUE
--------------------------------------------------------------------------------
If PROD_CURRENT_ENV turns out to be something confusing like "development" or
"local" and you later want it to read "production", this is what it costs — do
NOT bundle it with the work above:

  1. Snapshot RDS; enable/confirm S3 versioning.
  2. Server-side copy every object from the old env segment to the new one:
       aws s3 cp --recursive \
         s3://content-ai-studio/DIS/raw/<ns>/<OLD>/ \
         s3://content-ai-studio/DIS/raw/<ns>/production/
     Repeat for processed/ and generated/, for EVERY namespace.
  3. Rewrite the stored URLs in Postgres — dis_jobs.raw_storage_url,
     dis_jobs.payload_storage_url, dis_jobs.validation_report_url,
     dis_documents.raw_storage_url, dis_documents.payload_storage_url,
     and any asset_urls_json entries in dis_content_units.
  4. Rewrite the URLs inside each source_list.json blob.
  5. Flip ENVIRONMENT, restart, verify the Source Library is intact.
  6. Only then delete the old prefix, after a soak period.
Steps 3 and 4 are the ones that make this a real project rather than a copy.
