WHY THIS REWRITE: the version we built (platform admin manually creates users
and picks a project from a dropdown; single User.project_id; username+password
only) is the WRONG workflow. The correct workflow is:
  - Tenants (= Projects) each have an ORGANIZATION CODE (slug).
  - Regular users are NEVER created by the platform admin. They self-provision
    by entering the org code + signing in with their Microsoft account.
  - The same Microsoft account can belong to MANY tenants (one per org code),
    with a possibly different role in each.
  - Platform admin manages tenants (create/suspend/license) and, per tenant,
    manages the members' roles / active status / deletion.

PART A — TARGET WORKFLOW
--------------------------------------------------------------------------------

LOGIN SCREEN (one screen, replaces the current username/password-only page):
  [ Organization code ______ ]
  [  Sign in with Microsoft  ]      <- uses the org code above
  --- or use username and password ---
  [x] Platform administrator        <- checkbox
  [ Username ______ ]
  [ Password ______ ]
  [ Sign In ]

  Rules:
   - "Sign in with Microsoft": requires a valid org code -> Microsoft OAuth ->
     on return, user is found-or-created inside that tenant, then logged in and
     dropped straight into that tenant's CLUSTERS (no project dashboard).
   - Platform administrator checkbox TICKED: org code ignored; authenticate a
     platform super-admin by username + password -> Tenants dashboard.
   - Checkbox UNTICKED + username/password + org code: authenticate a tenant
     user that has a local password (e.g. the initial tenant admin) -> that
     tenant's clusters.

PLATFORM ADMIN (after ticking the box + creds):
  1. Lands on the TENANTS dashboard (screenshot image2/image8):
        NAME | CODE | USERS (n / max) | STATUS | [Users] [Roles] [Settings]
        + "New tenant" button (top-right).
  2. "New tenant" (image9) creates:
        - Organization code (slug)   e.g. "aim003"
        - Display name                e.g. "AIM 16 Block Development"
        - Max users (license)         e.g. 50
        - Initial tenant admin: username + password + display name
  3. "Users" on a tenant (image3/image6/image7): a per-tenant member table
        USERNAME | DISPLAY NAME | ROLE | STATUS | ACTIONS
        ACTIONS = edit role, deactivate/activate, delete.  "+ Add user".
  4. "Edit user" (image4): change display name, role, (optional) password,
        team, active flag. Username is read-only.
  5. Links to go into the tenant's CLUSTERS; the rest of Content AI Studio
        (clusters -> courses -> workspace) continues unchanged.

REGULAR USER:
  1. Enters the org code their organisation gave them.
  2. Clicks "Sign in with Microsoft", authenticates with their work account.
  3. First time: an account is auto-created in that tenant with the tenant's
     default new-user role. Returning: matched by Microsoft OID / email.
  4. Lands directly in that tenant's CLUSTERS. Never sees the project/tenant
     dashboard.
  5. To work in a DIFFERENT tenant: sign out, enter that tenant's org code,
     sign in with the SAME Microsoft account -> now a member there too.

PART B — TARGET DATA MODEL   (Project = Tenant)
--------------------------------------------------------------------------------

PROJECT (the tenant) — add columns to promptops_app/database.py `Project`:
  slug                    String(64)  UNIQUE, NOT NULL, indexed   <- org code
  max_users               Integer     default 50                  <- license
  status                  String(20)  default "active"            <- active|suspended
                          (or reuse existing is_active; see D-Phase1)
  microsoft_auth_enabled  Boolean     default True
  azure_tenant_id         String(64)  nullable   (per-tenant Azure app, optional)
  azure_client_id         String(64)  nullable
  azure_client_secret     String(512) nullable
  azure_new_user_role     String(32)  nullable   (role granted to self-provisioned users)
  allowed_email_domains   String(500) nullable   ("academian.com, foo.edu")
  display name            -> existing Project.name

USER + MEMBERSHIP — THE KEY DECISION (see PART E, Decision 1):
  A person can be in multiple tenants with a different role in each. Two ways:

  OPTION 1 (RECOMMENDED for Content AI Studio) — membership join table.
    Keep ONE global User row per person (username stays globally unique, so all
    existing code that joins by username keeps working). Add:
      users.microsoft_oid   String(64) nullable index
      users.email           String(255) nullable index
      users.display_name    String(200) nullable
      users.password_hash   already exists (nullable for Microsoft-only users)
    New table `tenant_memberships`:
      id, user_id FK->users.id, project_id FK->projects.id,
      role (tenant-scoped: admin|reviewer|author), active Bool,
      created_at, created_by
      UNIQUE(user_id, project_id)
    JWT carries the ACTIVE project_id for the session (chosen via org code at
    login). Role for the session = that membership's role.
    -> vpoal can be PROMPT MANAGER(reviewer) in academian and USER(author) in
       aim003 as two membership rows, one user row.

  OPTION 2 (exact prompt-library replica) — one User row per (tenant, person).
    Drop global-unique username; add composite UNIQUE(project_id, username),
    (project_id, email), (project_id, microsoft_oid). Much larger blast radius:
    every query/assignment/`created_by` that assumes global-unique username
    must be re-audited. NOT recommended unless exact parity is required.

ROLE MAPPING — prompt-library roles -> Content AI Studio roles (Decision 2):
  prompt-library         Content AI Studio (existing RBAC, keep vocabulary)
  -----------------      ------------------------------------------------
  tenant_admin      ->   admin      ("Director")   manages the tenant
  prompt_manager    ->   reviewer   ("Lead")
  user              ->   author     ("ID")
  platform_admin    ->   is_platform_admin flag (unchanged)
  The Users/Edit-User UI shows these three assignable roles + platform admin
  stays separate.
