WHAT WAS CHANGED (code, local only, not pushed)
--------------------------------------------------------------------------------
promptops_app/importers/package_extractor.py — raised the zip-bomb safety
guard (not a product size limit, a DoS backstop):
    MAX_UNCOMPRESSED_BYTES:  2 GB  -> 20 GB
    MAX_SINGLE_FILE_BYTES: 512 MB  ->  4 GB
Entry-count (50,000) and compression-ratio (200x) guards left unchanged —
those catch the actual zip-bomb pattern (a tiny archive claiming to expand to
a huge size), not large-but-honest packages, and don't scale with real course
content the way a byte ceiling does.

THIS IS NOT WHAT PRODUCED THE 413 YOU SAW
--------------------------------------------------------------------------------
Traced it precisely: nothing in this codebase returns 413. The only
size-related failure in the app itself is PackageValidationError, which the
router maps to HTTP 422 (app/api/v1/routers/imports.py). A 413 "Request
Entity Too Large" is generated by whatever reverse proxy / load balancer sits
in front of cas-dev-api.academian.com — and that config is NOT in this repo.

Confirmed by comparison: dis_backend/deploy/ec2_setup.sh provisions an nginx
site for DIS with an explicit `client_max_body_size 500M;`. There is no
equivalent file anywhere in this repo for the main CAS API. nginx's default
when a site config doesn't override it is `client_max_body_size 1m` — a
large IMSCC zip hitting that default lines up exactly with your screenshot.

MANUAL STEP STILL NEEDED (I don't have access to the dev/prod boxes)
--------------------------------------------------------------------------------
On whichever box serves cas-dev-api.academian.com:

  1. Find the nginx site config actually in use:
       sudo nginx -T | grep -B5 client_max_body_size
     or look in /etc/nginx/sites-available/ for the file whose server_name

  2. Inside that file's `server { }` block (the same block with `listen 443

     (matches the new 4 GB per-file code ceiling; bump both together if you

       sudo nginx -t && sudo systemctl reload nginx

  4. If it's an AWS ALB/API Gateway in front instead of (or in addition to)

I did not write a replacement nginx server block myself — the live one
almost certainly already has TLS certificate paths and other settings I
can't see or safely guess at, and overwriting it blind risks breaking HTTPS
