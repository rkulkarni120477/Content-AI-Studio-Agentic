# Technical Requirements - Content AI Studio Reverse Pipeline (Course Import)

**Feature:** Import an existing Canvas **IMSCC** course into CAS, reconstruct it in the Editor, and auto-derive the CDD, Blueprint, and Style - so an imported course becomes a fully editable, AI-native project.

**Version:** 1.0 · Draft for engineering · July 2026 **Audience:** CAS backend + frontend engineers

## 1\. Goals and the prime directive

**Goal A - Scratch path is untouched.** When a user picks _New Course_ (from scratch), the product behaves exactly as it does today. No regressions, no behavioural change, no shared code path that now carries an if import branch.

**Goal B - Import path is additive.** When a user picks _Import Existing Course_, a new, self-contained workflow runs: upload IMSCC → extract → parse → reconstruct Editor → auto-generate CDD, Blueprint, Style. The result is a normal CAS course that can subsequently be edited and re-generated by 20-50% (or any amount) across **Editor, CDD, Blueprint, Style, Workflow, and Analytics** - using the existing tools.

**Prime directive (non-negotiable):** _Reuse_ existing models, services, and UI, but keep the two paths **decoupled**. The import subsystem must never mutate the runtime behaviour of the scratch pipeline. Isolation is achieved by a single architectural rule (Section 4): **the importer produces the same database rows the scratch pipeline produces - it just fills them from parsed content instead of from an LLM design pass.** Everything downstream then works unchanged and is origin-agnostic.

## 2\. Complete user journey (end to end)

This is the experience we are building, told as a story. The technical sections that follow (3-17) explain how each step is implemented and kept isolated from the scratch path.

### 2.1 The fork - one button, two paths

- The user is inside a Course creation page and clicks **Create Course** (the existing button on CoursesPage).
- Instead of immediately creating a course, a **popup** appears with two choices (matching the mockup):
  - **New (Scratch) Course**
  - **Import Course**
- **If the user picks _New (Scratch) Course_** → the app behaves _exactly as it does today_. It calls the current createCourse endpoint and drops the user into the normal Style → CDD → Blueprint → Generate → Editor → Export workflow. **Nothing about this path changes.** (Goal A.)
- **If the user picks _Import Course_** → the app routes to a new **Import page**. (Goal B - everything below.)

### 2.2 Import - upload the IMSCC package

- On the Import page the user uploads an **IMSCC** package (v1 supports IMSCC only; the uploader is built so other formats can be added later without rework).
- The system runs a quick **validation** and shows what it found - number of modules, pages, quizzes, assignments, discussions, and resource files - plus any items it can't fully reconstruct (e.g. external LTI links), surfaced as warnings, not blockers.
- The user confirms and clicks **Start Import**.

### 2.3 Behind the scenes - everything runs on a background queue

- The heavy work does **not** block the browser. A background **job** is enqueued and the user watches a **live progress screen** (or leaves the page and comes back). The job moves through clear stages, each reporting progress:
  - **Extract** the package.
  - **Parse** the Canvas content (modules, pages, quizzes, discussions, resources).
  - **Reconstruct Editor** - rebuild the course structure and content blocks exactly as the original.
  - **Reverse-generate Blueprint** - derive per-module objectives and assessments from the real content.
  - **Reverse-generate CDD** - derive the course-wide design (audience, outcomes, tone, standards).
  - **Analyse Style** - detect the course's writing style and save it as a reusable Style.
- If a single item fails (e.g. one malformed page), the job retries it and, if still failing, flags it for review and continues - the import never dies on one bad item. Fatal problems (corrupt zip, no manifest) fail cleanly with a readable message.

### 2.4 After import - a fully editable, AI-native course

- When the job completes, the user opens the course workspace and finds every tab already populated:
  - **Editor tab** - displays the imported course content, organised into the same modules and pages as the original, **and it is fully editable** - exactly the same editing experience as content that CAS generates itself (inline edit, autosave, version history, per-block regenerate, workflow states).
  - **CDD tab** - shows a Course Design Document **created from the uploaded course**, editable and regenerable.
  - **Blueprint tab** - shows per-module blueprints **derived from the uploaded course**, editable and regenerable.
  - **Style tab** - shows the detected Style, editable and reusable.
- From here the imported course is indistinguishable from a scratch course. The user can **edit anything and regenerate any amount** - a light 20% polish or a full-course rewrite - across Editor, CDD, Blueprint, and Style, and move blocks through the normal **Workflow** (Draft → In Review → Approved → Published). It shows up in **Analytics** like any other course.

### 2.5 Round-trip - pack it back up

- When the user has finished editing, they go to **Export** and **pack the course back into an IMSCC package** using the existing CAS export engine - ready to re-import into Canvas. Because the import kept a provenance map (which imported item became which CAS block), the round-trip stays high-fidelity.

**In one line:** _Create Course → pick Import → upload IMSCC → watch the queue reconstruct it → edit the Editor/CDD/Blueprint/Style like any AI-native course → export back to IMSCC._ The scratch path is never touched.

## 4\. Design principle - "same rows, different origin"

The reverse pipeline adds **one new subsystem** (Import & Reconstruction). It does **not** thread import logic through existing services. Instead:

Scratch path: Style/CDD/Blueprint (LLM) ──► Generate (LLM) ──► Generation+Block rows ──► Editor  
Import path: IMSCC ──► Parse ──► Editor Builder ──────────► Generation+Block rows ──► Editor  
└► Reverse CDD/Blueprint/Style (LLM from content) ──► version rows

Both paths converge on identical row shapes. Downstream code never asks "where did this come from" to decide behaviour. A single optional metadata flag (courses.source_type) exists only for **display/analytics** (a badge, a filter) - it must never gate core logic.

## 5\. Reverse pipeline architecture

New subsystem (all new files; nothing existing is edited except the additive touchpoints in Section 10):

promptops_app/importers/ ← NEW package (mirror of exporters/)  
imscc_importer.py orchestrator: validate → extract → parse → build → reverse-gen  
package_extractor.py unzip, locate imsmanifest.xml, stage resource files  
canvas_parser.py manifest + module_meta + wiki_content + assessments → InternalCourseModel  
internal_model.py dataclasses: ICourse, IModule, IPage, IAssessment, IResource (+ provenance ids)  
editor_builder.py InternalCourseModel → Generation/Block/CourseModule rows (reuses block-persist pattern)  
reverse_cdd.py reconstructed content → CDD prompt → CDDVersion (reuses llm_service + cdd_repository)  
reverse_blueprint.py per-module content → Blueprint prompt → BlueprintVersion  
style_analyzer.py sampled content → Style prompt → Style/StyleVersion (reuses style_service)  
provenance.py write/read Canvas-item ↔ CAS-block map (round-trip fidelity)  
<br/>promptops_app/jobs/  
import_jobs.py run_import_job(job_id): drives the stages, updates GenerationJob progress  
<br/>app/api/v1/routers/  
imports.py NEW router: upload/validate, start, status, cancel

**Pipeline stages** (each updates job progress/current_step):

- **Validate** - is it a real IMSCC 1.1 package? (imsmanifest.xml present, readable). Return structure counts + unsupported items (e.g. external LTI) as warnings.
- **Extract** - unzip to a temp workspace; stage web_resources/ and other assets.
- **Parse** - walk manifest organizations (TOC) + module_meta.xml for module order; parse each wiki_content/\*.html page and assessment/\*.xml quiz (via qti_parser) into the InternalCourseModel, capturing a stable provenance id per item.
- **Reconstruct Editor** - editor_builder creates one CourseModule per Canvas module and Generation+Block rows per page/assessment (HTML→markdown for Block.content). Blocks start in workflow_state="draft".
- **Reverse-generate Blueprint** - per module, summarise reconstructed content and ask the LLM to derive objectives / key concepts / assessments → BlueprintVersion (active) → pin active_blueprint_id.
- **Reverse-generate CDD** - from the blueprint set + course-level content, derive audience / outcomes / tone / quality standards → CDDVersion (active) → pin active_cdd_id.
- **Style analysis (optional)** - sample reconstructed prose, derive a reusable Style → pin active_style_id.
- **Finalize** - mark job complete, persist provenance map, set courses.source_type="imscc".

Ordering note: Blueprint before CDD mirrors the natural inference direction (content → module structure → course design). Reconstruction (stage 4) must fully succeed **before** stages 5-7; if reverse-generation fails, the course is still usable (Editor is populated) and reverse-gen can be retried independently.

## 9\. Editor reuse (the core of Goal B)

No Editor changes. The Editor already renders whatever listCourseBlocks(courseId) returns. The editor_builder maps:

| Canvas item                            | CAS row                                                                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Module (from module_meta.xml, ordered) | CourseModule(course_id, title, position)                                                                                 |
| Wiki page (wiki_content/x.html)        | Generation(block_type="lesson", course_id, …) + Block(block_type="lesson", content=&lt;html→md&gt;, module_id, position) |
| Assessment (assessment/x.xml, QTI)     | Block(block_type="quiz"/"assignment", content=&lt;normalised questions&gt;, module_id)                                   |
| Cited/embedded resource                | Source Library document (via file_parser) + \[Source: filename\] references preserved in block content                   |

Because blocks are created in draft, the existing Workflow (Draft → In Review → Approved → Published), Version History (BlockVersion on edit/regenerate), autosave, and per-block **regenerate** all function immediately. That satisfies "imported course can be updated 20-50% (or any amount)" with **zero** new editor logic.

## 10\. Reverse-generation of CDD / Blueprint / Style

Each reuses the existing persistence + activation path so the CDD/Blueprint/Style tabs render normally:

- **Blueprint:** for each CourseModule, build a content summary → call llm_service with reverse_blueprint prompt → parse into the same sections shape the forward blueprint uses (blueprint_parser) → blueprint_repository.create_version(..., is_active=True) → set courses.active_blueprint_id.
- **CDD:** aggregate module blueprints + course metadata → reverse_cdd prompt → cdd_parser → cdd_repository.create_version(..., is_active=True) → set courses.active_cdd_id.
- **Style:** sample N reconstructed lessons → style_analysis prompt → style_service create + courses.active_style_id.

**Editability after import (Goal B):** these are ordinary active versions. The user edits them with the existing CDD/Blueprint/Style editors and existing **regenerate** endpoints.

**Sync policy (deliberately conservative to honour "don't interfere"):** v1 does **not** auto-cascade regeneration between artifacts. Edits are independent; the user triggers regeneration explicitly via the existing controls. A "N sections may be stale" hint (from a simple updated_at comparison) may be surfaced, but automatic cross-artifact regeneration is **out of scope for v1** precisely because it risks the interference the prime directive forbids. (Bidirectional auto-sync is a Phase-2 opt-in.)

## 12\. Background job & progress

Reuse GenerationJob with job_type="import":

- input_payload_json = { import_id, course_id, options }.
- current_step cycles: Extracting → Parsing (n/m pages) → Reconstructing Editor → Blueprint → CDD → Style → Done.
- result_entity_id = course_id (so the UI can deep-link).
- Errors: per-item failures are retried once, then recorded in warnings_json and skipped (import never hard-fails on a single bad page). Fatal errors (corrupt zip, no manifest) fail the job with a clean error_message.

run_import_job lives in a **separate** module (jobs/import_jobs.py) and shares **only** the generic job-runner utilities - it does not call run_generation_job.

## 13\. Isolation & non-interference rules (the guardrails)

**Do:** - Add new files/tables/columns/endpoints/prompts. Keep all import code under importers/, jobs/import_jobs.py, app/api/v1/routers/imports.py, features/import/. - Reuse existing **repositories/services** in an append/read manner (create rows, read config) - the same calls the scratch pipeline already makes. - Gate the whole feature behind a config flag IMPORT_PIPELINE_ENABLED (default off in prod until QA sign-off). When off, the create-course modal shows only "New Course" and the router is not mounted.

**Don't:** - Don't add if source*type == "imscc" branches inside generation_jobs.py, editor thunks, or the CDD/Blueprint/Style/Workflow/Analytics endpoints. Those stay origin-agnostic. - Don't modify existing columns, existing endpoint contracts, or existing prompt templates. - Don't let reverse-generation reuse the \_scratch* generation entrypoint (run_generation_job); it has its own orchestrator. - Don't auto-cascade regeneration across artifacts in v1.

**Shared-code contract:** any existing function the importer calls must be used exactly as the scratch path uses it (same arguments, same side effects). If the importer needs different behaviour, it gets a **new** function - never a new parameter on an existing hot-path function.

## 15\. Acceptance criteria

**Goal A (regression-free scratch path):** - Creating a course from scratch and running Style → CDD → Blueprint → Generate → Editor → Export produces identical results to the current build (verified against characterization tests in tests/characterization). - With IMPORT_PIPELINE_ENABLED=false, the app is byte-for-byte behaviourally equivalent to today except the create-course modal (which, choosing "New Course", calls the identical endpoint). - No existing endpoint contract, column, or prompt changed.

**Goal B (import path):** - Uploading a valid Canvas IMSCC package reconstructs ≥95% of modules/pages/assessments into the Editor, correctly ordered and grouped. - CDD, Blueprint, and Style tabs are auto-populated from the imported content and are individually editable and regenerable. - The imported course flows through Workflow (Draft→…→Published) and appears in Analytics like any other course. - The user can edit/regenerate any portion (small tweaks up to full-course regeneration) using existing tools, with Version History captured. - Export produces a valid IMSCC package (round-trip) via the existing engine.

## 16\. Risks & mitigations

| Risk                             | Mitigation                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Malicious/oversized packages     | Zip-bomb + path-traversal guards; size cap; process in isolated temp dir; tenant-scoped.                                              |
| Imperfect HTML→markdown fidelity | Keep original HTML on the block (content_html already exists) as fallback; provenance enables faithful re-export.                     |
| Reverse-gen LLM quality variance | Reconstruction (Editor) is independent of reverse-gen; reverse-gen is retryable; quality is a soft target, structure is the hard one. |
| Accidental coupling creeping in  | Code review checklist enforcing Section 13; feature flag; import code confined to its own packages.                                   |
| Large courses blocking a worker  | Background job with progress; chunked parsing; per-item retry.                                                                        |

## 17\. Out of scope (v1)

SCORM/Moodle/Brightspace import; automatic bidirectional artifact sync; AI modernization suggestions; standards mapping; bulk/batch migration; automated quality scoring. (All are natural Phase-2+ extensions enabled by the pluggable parser and provenance map.)
