AIM document types in DIS

Every Aviation Institute of Maintenance file ingested by the Document Intelligence Service is classified, chunked, and written to more than one store. This document explains each stored document type: typical source files, which code path parses it, the chunking strategy, and what lands in S3 versus Postgres (with OpenSearch embeddings).

How DIS stores AIM files

AIM is tenant aim in namespace aim_ns. Config lives in dis_backend/config/clients/aim.yaml. Ingestion is one shared pipeline (services/pipeline/graph.py); AIM-specific behavior is a profile overlay (services/client_profiles/aim.py) plus two specialized parsers (teacher calendars and AKTR rollups).

Write path (every successful ingest)

  1. Raw bytes go to S3.
  2. Extractors turn the file into text / tables / slides.
  3. Classifier + AIM profile set document_type / content_type.
  4. Specialized structure extractors run for calendar, syllabus, quiz, project, AKTR.
  5. content_unit_creation splits the file into units (the real chunks).
  6. Processed JSON artifacts go to S3.
  7. Rows go to Postgres (dis.* + source_index).
  8. Each unit is embedded (Titan v2, 1024-d) and indexed in OpenSearch.

Live generation retrieval still reads the S3 Source Library JSON (source_content/content.json). Postgres and OpenSearch are populated at ingest as the relational system-of-record and the semantic index. Digests (CDD / Blueprint MAP) do read Postgres content units.

The pipeline classifier uses academic type names from document_processing.enabled_document_types. The AIM profile then remaps many of those to Source Library / generation types. What you see stored on the document is usually the remapped content_type.

Chunking layers

AIM YAML says chunking_strategy: semantic, chunk_size: 512, chunk_overlap: 64. That is only the fallback word-chunk. Two later policies override it.

1. Pipeline units — content_unit_creation_agent.py

  • Per-day if a calendar structure has days[].
  • Per-block sheet if an AKTR structure has blocks[].
  • Per-slide if the extractor produced slide_texts (PPTX).
  • Whole document (one unit, no overlap) for style / CDD / blueprint types, including syllabus and any file flagged use_for_blueprint.
  • Semantic word chunks otherwise: 512 words, 64-word overlap.

2. Source Library view — source_library.py

  • per_unit — keep pipeline units (AKTR only).
  • full_document — concatenate all unit text into one CAS unit (calendars, syllabi, other CDD/blueprint).
  • semantic_chunk — keep pipeline chunks (lessons, quizzes, projects, slides).

Retrieval reads this clean file, not the raw pipeline payload.

Quiz / project structure extractors detect questions and tasks, but they do not currently create one unit per question. Units stay word-chunks (or one full document); unit_type is only a label (quiz_question, project_task, …).

course_calendar

Per-day units Source Library: full_document instructor_only blueprint + cdd S3 Postgres OpenSearch

Source of truth for what happens on each block day: topics, ACS codes, handbook pages, quizzes, projects, hangar work.

Typical files

  • Folder: Teaching Outline & Syllabus
  • Names like Block 6 Teacher Calendar.xlsx, B1 Student Version.xlsx
  • Allowed: .xlsx (AIM parser), or PDF/DOCX via the generic row extractor

Which files process it

  • services/aim_calendar.py — column-aware AIM teacher-calendar workbook parser
  • services/specialized_extractors.py → extract_calendar_structure (generic fallback)
  • services/agents/specialized_structure_extraction_agent.py
  • services/agents/content_unit_creation_agent.py — one unit per days[] row
  • services/indexing.py → upsert_calendar

Chunking strategy

Not word-chunked. Each teaching day becomes one calendar_day unit. Embeddings use a composed sentence, not raw spreadsheet cells (“Block 6, Day 3 — Aircraft Drawings (Day 2 of unit). Topics covered: … ACS codes: …”). Source Library then concatenates all days into one full_document so CAS can view the whole calendar.

Where data is stored

  • S3 — raw XLSX; calendar_structure.json; all content units; content.json
  • Postgres — dis_course_calendars (full structure JSON) + dis_calendar_days (one row per day) + dis_content_units
  • OpenSearch — one vector per day, tagged with block, day_number, ACS codes

syllabus

Whole document (1 unit) Source Library: full_document student cdd + blueprint S3 Postgres OpenSearch

Authoritative course description, outcomes, grading, and attendance. Kept whole so rule order is not split across chunks.

Typical files

  • Folder: Teaching Outline & Syllabus
  • Names containing syllabus; PDF or DOCX

Which files process it

  • services/specialized_extractors.py → extract_syllabus_structure
  • services/agents/specialized_structure_extraction_agent.py
  • services/indexing.py → upsert_syllabus

Chunking strategy

Pipeline treats syllabus as a CDD/blueprint type: one unit covering the entire extracted text (chunk_overlap = 0). Source Library also stores it as full_document. Structured fields (outcomes, grading, attendance) are parsed into a sidecar object, not extra chunks.

Where data is stored

  • S3 — raw file, syllabus_structure.json, one content unit, clean content
  • Postgres — dis_syllabus (description, outcomes JSON, policies) + dis_content_units
  • OpenSearch — one embedding of the whole syllabus (clipped at 24,000 chars if huge)

Example structure stored

{
  "structure_type": "syllabus",
  "course_name": "General Science I Syllabus",
  "block": "Block 1",
  "course_description": "Course description This course introduces…",
  "learning_outcomes": ["Identify standard aviation measuring tools", "Apply weight-and-balance computations"],
  "materials": ["FAA-H-8083-30B", "FAR/AMT"],
  "grading_policy": "Grading Quizzes 20% Projects 40% Final exam 40%…",
  "attendance_policy": "Attendance Students must attend…"
}

knowledge_test_report

Per-block sheet Source Library: per_unit instructor_only cdd + blueprint S3 Postgres OpenSearch

AKTR (Airman Knowledge Test Report) missed-code rollup. Cohort performance, not exam questions. One workbook covers the whole program (a sheet per block).

Typical files

  • ALLCAMPUS_AKTR_MissedCodes_Q12026.xlsx
  • Filename keywords: aktr, missedcodes, missed codes

Which files process it

  • services/knowledge_test_report.py — sheet-aware workbook parser
  • specialized_structure_extraction_agent.py (checked before quiz rules so it is not typed as an answer key)
  • content_unit_creation_agent.py — one unit per block sheet

Chunking strategy

Must not be word-chunked. A 512-word split would cut a block table in half and stamp every sheet with the first sheet’s block. Instead: one knowledge_test_item per block, each carrying its own block / acs_codes. Document-level block is left blank (spans_multiple_blocks: true). Source Library keeps per_unit so Block 6 retrieval sees only the Block 6 sheet.

Where data is stored

  • S3 — raw XLSX; units in payload + content.json (one clean unit per block, with a short metadata allow-list)
  • Postgres — dis_content_units only (no dedicated AKTR table); catalog row in source_index
  • OpenSearch — one vector per block sheet

Example unit

{
  "content_unit_id": "job_abc:knowledge_test_6",
  "unit_type": "knowledge_test_item",
  "title": "ALL CAMPUS — Block 6 | Top 10 Most Missed ACS Codes",
  "text": "ALL CAMPUS — Block 6 | Top 10 Most Missed ACS Codes\n#1 — AM.II.K.K1 — 48.2% missed — Basic electricity principles\n#2 — AM.II.K.K4 — 41.0% missed — Series and parallel circuits",
  "metadata": {
    "document_type": "knowledge_test_report",
    "block": "Block 6",
    "block_number": 6,
    "block_id": "B6",
    "sheet_name": "Block 6",
    "acs_codes": ["AM.II.K.K1", "AM.II.K.K4"],
    "missed_codes": [
      {"acs_code": "AM.II.K.K1", "pct_missed": 0.482, "rank": 1, "description": "Basic electricity principles"}
    ],
    "visibility": "instructor_only",
    "restricted": false
  }
}

lesson_pdf

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Finalized daily lesson deck exported as PDF. Filename day is trusted (mapped_day).

Typical files

  • Folders: Finalized PDFs, Final PDFs (source_priority 1)
  • B1D17 - Weight and Balance - Day 4.pdf

Which files process it

  • services/pipeline/extractors.py → extract_pdf (pdfplumber / PDFium; tables when small)
  • services/client_profiles/aim.py — remaps folder + B#D# to lesson_pdf
  • No specialized structure extractor; generic sections + word chunks

Chunking strategy

Semantic word chunks: 512 words, 64 overlap. unit_type = page. Day comes from B1D17 in the filename. Archive / 1-Original / 2-Edited copies are stored for traceability but marked exclude_by_default / internal_only.

Example stored metadata

  "content_type": "lesson_pdf",
  "source_file_name": "B1D17 - Weight and Balance - Day 4.pdf",
  "block_id": "B1",
  "day_id": "B1D17",
  "day_number": 17,
  "mapped_day": "B1D17",
  "title": "Weight and Balance Day 4",
  "topic": "Weight and Balance",
  "version": "pdf_final",
  "visibility": "student",
  "use_for_course_generation": true,
  "source_priority": 1
}

Each Postgres / OpenSearch unit looks like:

{
  "content_unit_id": "job_abc:unit_2",

  "unit_number": 2,

slide_deck

Per-slide student course_generation S3 Postgres OpenSearch

PowerPoint lecture. Classifier name is often lesson_slide_deck; AIM stores slide_deck.

Typical files

  • Folder: Final Slide Deck
  • B1D17 Weight and Balance.pptx (or any .ppt / .pptx)

Which files process it

  • extractors.py → extract_pptx (per-slide text; optional image extract)
  • visual_understanding_agent.py — Claude Vision captions when vision_enabled: true
  • content_unit_creation_agent.py — iterates slide_texts

Chunking strategy

One slide unit per slide (not 512-word chunks). Title is the first non-marker line. visual_summary is attached by slide number. AIM fast path: fast_pptx_enabled, max 200 slides.

Example unit

{
  "content_unit_id": "job_abc:slide_4",
  "unit_type": "slide",
  "unit_number": 4,
  "title": "Today’s Focus — CG Shift",
  "text": "[Slide 4]\nToday’s Focus\n• How CG moves when fuel is burned\n• Worked example",
  "visual_summary": "Diagram of an aircraft with CG arrow moving aft as fuel tanks empty.",
  "metadata": { "slide_number": 4, "document_type": "slide_deck", "day_id": "B1D17" }
}

quiz

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Student quiz. Calendar mapping is required; filename day is only a suggestion.

Typical files

  • Preferred folders: Quizzes/5-PDFs/Updated PDFs, then Quizzes/4-Finalized/Updated Quizzes
  • B2Q1.docx, Block 2 Quiz 1 - Aircraft Drawings.pdf

Which files process it

  • PDF/DOCX extractors
  • extract_quiz_structure — counts lines that look like 1. / Q1 / Question
  • AIM profile sets quiz_number, quiz_id (B2Q1)

Chunking strategy

Word chunks of 512 / 64. unit_type is labeled quiz_question even when a chunk holds several questions. Structure JSON stores question_count_detected and a 20-question preview; it is not one-row-per-question storage.

Example metadata

{
  "document_type": "quiz",
  "quiz_number": 1,
  "quiz_id": "B2Q1",
  "suggested_day_from_filename": "B2D4",
  "mapped_day_source": "calendar_required",
  "calendar_mapping_required": true,
  "visibility": "student",
  "restricted": false
}

Quiz structure artifact:

{
  "structure_type": "quiz_exam",
  "quiz_title": "B2Q1",
  "question_count_detected": 12,
  "questions_preview": ["1. What does a hidden line represent?", "2. …"],
  "is_answer_key": false

final_exam

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Same storage path as quiz. Typed when the name contains final exam, cumulative exam, or a leftover bare test after other heuristics.

Typical files

  • Quizzes/5-PDFs/Block 2 Final Exam.pdf

Chunking / storage

Identical to quiz: 512-word chunks, unit_type = quiz_question, calendar-first mapping, student visibility. Retake folders are excluded by default.

project

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Student project / lab. Classifier may say project_activity.

Typical files

  • Preferred: Projects/4-PDF, then Projects/3-Final
  • Block 6 Project 6-1 Weight and Balance.pdf

Which files process it

  • extract_project_structure — objectives, materials, procedure, assessment sections
  • AIM profile sets project_number / project_id (B6P6-1)

Chunking strategy

512 / 64 word chunks labeled project_task. Structure fields are sidecar JSON, not one unit per task. Calendar decides the administered day (mapped_day_source: calendar_required).

hangar_activity

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Shop / hangar practical. Typed when the path or name contains hangar (folder Hangar Activities wins over a stray word like “test” in the title).

Chunking / storage

Same as project: PDF/DOCX extract + 512-word chunks. unit_type = activity. Calendar-first day mapping. No dedicated hangar table — units + S3 payload only.

study_questions

Semantic 512 / 64 student course_generation S3 Postgres OpenSearch

Self-study / review questions. Folder Study Questions.

Chunking / storage

512 / 64 word chunks, unit_type = study_question. Calendar mapping required. No specialized per-question splitter (same as quizzes).

quiz_answer_key

Semantic 512 / 64 restricted / instructor_only S3 Postgres OpenSearch

Quiz key. Detected from Answer Key, Quiz Key, or compact B2Q1.Key.docx.

Which files process it

  • Same quiz structure extractor, with is_answer_key: true
  • Listed in restricted_document_types and restricted_filename_contains

Chunking / storage

512-word chunks labeled answer_key_item. Stored in S3, Postgres, and OpenSearch like any other file, but retrieval gates hide it from student / course-generation context unless an admin sets include_restricted: true. 

{
  "document_type": "quiz_answer_key",
  "visibility": "instructor_only",
  "restricted": true,
  "access_level": "admin_only",
  "use_for_course_generation": false
}

final_exam_answer_key

Semantic 512 / 64 restricted / instructor_only S3 Postgres OpenSearch

Same as quiz keys when the name also contains final exam. Unit type answer_key_item. Never used for student-facing generation.

project_instructor_guide

Semantic 512 / 64 restricted / instructor_only S3 Postgres OpenSearch

Pipeline types project_key and instructor_guide remap here. Also any project file whose name looks like a key (… Key.pdf).

Typical files

  • Projects/4-PDF/Project 6-1 Instructor Guide.pdf

Chunking / storage

Project structure extractor runs (is_instructor_guide: true). Units are 512-word chunks labeled guide_section. Same three stores; restricted from student retrieval.

ebook_reference

Semantic 512 / 64 reference / assigned reading S3 Postgres OpenSearch

FAA handbooks and similar long PDFs (FAR-AMT, FAA-H-8083-30B).

Which files process it

  • extract_pdf — files over 40 MB skip pdfplumber and use PDFium (tables sacrificed)
  • Digest worksheets join dis_content_units where document_type = 'ebook_reference'

Chunking strategy

Long-document semantic chunks (512 / 64), unit_type = page. Embedding input is clipped at 24,000 characters per unit so Titan’s 8,192-token limit is not exceeded. CAS View may split the concatenated text into synthetic pages for the UI only; retrieval still uses the stored chunks.

student_handout

Semantic 512 / 64 student (typical) S3 Postgres OpenSearch

Enabled pipeline type for leftover student worksheets that did not match a stronger rule. unit_type = chunk. Same three-store write path as lessons.

other

Semantic 512 / 64 S3 Postgres OpenSearch

Fallback when filename/text rules and the LLM classifier do not agree on a type (fallback_doc_type: other). AIM folder heuristics often rescue these (Finalized PDFs → lesson_pdf, Hangar → hangar_activity). If it remains other: 512-word chunks, unit_type = chunk, purpose general_reference, usually not used for blueprint or course generation.

End-to-end examples

1. Teacher calendar (XLSX)

File → AIM parser → 20 day units → S3 + 3 Postgres tables + 20 OpenSearch vectors

Source: Teaching Outline & Syllabus/Block 6 Teacher Calendar.xlsx

S3 raw:
  DIS/raw/aim_ns/development/{job}/Block 6 Teacher Calendar.xlsx

S3 processed extras:
  .../extracted/calendar_structure.json     # days[20] with ACS, quiz, handbook_refs
  .../extracted/content_units.json          # 20 calendar_day objects
  .../source_content/content.json           # chunking_strategy: "full_document", 1 CAS unit

Postgres:
  dis_documents          1 row  document_type = course_calendar
  dis_course_calendars   1 row  total_days = 20, structure_json = full parse
  dis_calendar_days     20 rows day_number, topic, source_text
  dis_content_units     20 rows unit_type = calendar_day
  source_index           1 row  purpose = blueprint, content_key → content.json

OpenSearch index dis-content-dev-aim:
  20 docs, each with titan embedding of that day's source_text

2. Lesson PDF

Source: Finalized PDFs/B1D17 - Weight and Balance - Day 4.pdf

Pipeline: extract_pdf → classify lesson_slide_deck/other → AIM remap lesson_pdf
          → no specialized structure → words.split() in steps of 448 (512-64)

If the PDF yields ~3,200 words → about 8 page units.

S3: raw PDF + extracted_text.json + content_units.json + content.json
    (chunking_strategy: "semantic_chunk", total_units: 8)

Postgres: dis_documents + 8 × dis_content_units (unit_type = page)
          source_index.day = 17, block = "Block 1"

OpenSearch: 8 vectors, filterable by day_id = B1D17

3. AKTR workbook

Source: ALLCAMPUS_AKTR_MissedCodes_Q12026.xlsx   (16 block sheets)

Pipeline: looks_like_aktr_report → build_knowledge_test_structure
          → 16 knowledge_test_item units (not 16×10 word chunks)

Document metadata: block = "", spans_multiple_blocks = true
Each unit metadata: block = "Block N", acs_codes = [...], missed_codes = [...]

S3 content.json: chunking_strategy = "per_unit"  (units kept, not concatenated)
Postgres: 16 content units; no dis_calendar_days / dis_syllabus rows
A Block 6 CDD/Blueprint query matches only the Block 6 unit

What is not stored as its own table

Quizzes, projects, hangar activities, study questions, slides, lessons, ebooks, and keys do not have dedicated Postgres tables. They share dis_documents + dis_content_units + S3 JSON. Only calendars and syllabi get extra relational tables because they are structural join sources for the rest of the curriculum.
